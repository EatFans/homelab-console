# HomeLab Panel 页面与交互规划

## 设计目标

Panel 是家庭平板控制端，优先服务于“走近屏幕、扫一眼、点一下”的日常使用。借鉴车机界面稳定导航、状态醒目、控件易点和操作路径短的特点；它仍是家庭平板应用，不受驾驶场景的专门限制。

第一版以横向平板为主要设计画布，同时按窗口宽度适配竖屏与较窄窗口。不要把布局绑定到设备型号或强制横屏。

## 页面地图

```text
首次使用 / 未配置 Hub
└── 连接中枢：手动填写地址 → 检查连接 → 完成连接

日常使用
├── 总览（默认首页）
│   ├── 家庭状态与常用设备
│   ├── 常用场景快捷操作
│   └── 告警、连接状态及相关入口
├── 房间
│   ├── 房间列表 / 切换
│   └── 房间内设备 → 设备详情面板
└── 场景
    ├── 场景列表
    └── 场景执行结果

次级入口
├── 系统状态与通知
└── 设置：Hub 连接、设备管理、界面偏好
```

主导航保持为 **总览、房间、场景** 三项。设备是操作对象，常用设备直接出现在总览和房间中；“全部设备”和管理类操作放进次级入口，减少日常导航项。若 Hub 第一版尚无场景能力，先隐藏或禁用“场景”，不要放空白功能页。

| 页面 | 用户要完成的事 | 首版内容 |
| --- | --- | --- |
| 连接中枢 | 配置并确认可用的 Hub | 手动输入地址、连接检查、失败原因与重试 |
| 总览 | 一眼看到家庭状态并执行高频操作 | Hub 状态、常用设备、常用场景、重要异常 |
| 房间 | 按空间找到并控制设备 | 房间切换、设备状态与直接控制 |
| 设备详情面板 | 查看更多状态和控制项 | 当前状态、控制反馈、最近更新时间；具体控件随设备类型确定 |
| 场景 | 一次完成一组家庭操作 | 可用场景与执行反馈；由 Hub 能力决定是否上线 |
| 设置 | 做低频配置和管理 | Hub 地址、重连、设备管理与界面偏好 |

## 主屏布局

横向宽屏的初稿：

```text
┌────────┬──────────────────────────────────────────────┬───────────────────┐
│        │ 顶部：家庭 / 时间 / Hub 状态 / 通知 / 设置    │                   │
│ 总览   ├──────────────────────────────────────────────┤ 家庭状态          │
│ 房间   │ 常用场景                                     │ 温度、告警等      │
│ 场景   ├──────────────────────────────────────────────┤                   │
│        │ 常用设备卡片 / 房间概览                       │ 需要关注的事项    │
│        │                                              │                   │
└────────┴──────────────────────────────────────────────┴───────────────────┘
```

左侧导航位置固定。顶部状态区始终能看到 Hub 在线、连接中或离线；时间只在应用采用沉浸式显示、系统状态栏不可见时展示。主区用清晰的大卡片呈现高频设备和场景；右侧状态栏只放确有价值的家庭数据，内容不足时让主区扩展，不保留空栏。

房间页可以采用“房间列表 + 设备网格”的双栏布局。点设备卡片时在右侧展开详情，返回后保留所在房间和滚动位置。场景页则使用大按钮或卡片，让场景名称、影响范围和执行状态一眼可辨。

窄窗口把左侧导航改为底部导航，主区改为单列；设备详情改为独立页面或全屏面板。按可用宽度而不是“平板/手机”判断布局，断点以实际内容拥挤程度为准。Flutter 的 [自适应布局建议](https://docs.flutter.dev/ui/adaptive-responsive/general)以约 600 逻辑像素作为底部导航与侧栏切换的参考值。

## 操作规则

1. **高频操作就近完成**：安全、可立即撤销的动作可在设备卡片上直接执行；详细调节从卡片进入详情面板。
2. **状态先于动画**：控制后显示发送中、已确认或失败；只有 Hub 确认后才把设备显示为成功状态。离线与过期数据明确标注，不能把缓存值当作实时值。
3. **危险操作加确认**：门锁、警报、车库门等敏感控制需要清晰的目标与确认步骤。不要只靠长按或手势发现功能。
4. **保持位置**：切换主导航后返回，尽量恢复之前选中的房间与列表位置；同一操作尽量在两到三步内完成。
5. **触控优先**：主操作区域做大、间距充足，图标始终配文字。颜色既表达设备类型，也表达状态，但不单独依赖颜色传递在线、离线或失败信息。

深色界面可作为首选视觉方向，但需保证白天与夜间都能读清。车机的 [视觉原则](https://developers.google.com/cars/design/design-foundations/visual-principles)强调一眼可读、一致性和较大的触控目标；具体尺寸应在目标平板上实测，不直接照搬车载设备的标准。

## 对应的 Flutter 功能模块

页面稳定后，按需要扩展现有 `lib/features/`：

```text
features/
├── dashboard/       总览
├── hub_connection/  首次连接与连接状态
├── rooms/           房间切换和房间设备
├── devices/         设备详情与控制反馈
├── scenes/          场景列表与执行反馈
└── settings/        低频配置
```

多个页面共用的 Hub 状态、设备数据和控制命令应来自共享 Repository，页面不直接发送网络请求。导航外壳、路由和各功能目录等到对应页面开始实现时再加入；当前代码只有总览占位页。

## 落地顺序

1. 设计横屏总览、房间页、设备详情面板与窄屏布局的线框，并在目标平板上检查可读性和可点性。
2. 做应用导航外壳与连接中枢页面，让离线、连接中、已连接三种状态可见。
3. 与 Hub 对齐设备及房间数据契约，再接入只读状态。
4. 接入单设备控制及结果反馈，随后加入场景。

参考：[Android Automotive 主导航](https://developers.google.com/cars/design/automotive-os/apps/media/interaction-model/navigating)、[车载内容层级](https://developers.google.com/cars/design/automotive-os/apps/media/create-your-app/plan-browsing-views)、[Flutter 大屏适配](https://docs.flutter.dev/ui/adaptive-responsive/large-screens)。这些资料提供交互启发，页面内容与控件密度仍以家庭平板实测为准。
