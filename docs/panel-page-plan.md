# HomeLab Panel 页面与交互规划

## 当前已落地的框架

Panel 目前有两个一级 Tab，底部使用悬浮的胶囊式切换栏。切换栏借鉴 iOS 分段控件的滑动选中效果，但应用仍运行在 Android 与 iOS 平板上。

```text
HomeLab Panel
├── 应用（默认 Tab，可纵向滚动）
│   ├── 房间、设备、场景、灯光、环境、窗帘
│   ├── 音乐、安防、摄像头、能耗、自动化、设置
│   └── 点击图标 → 对应标题的占位功能页 → 返回应用
└── 总览（第二个 Tab，内容待设计）
```

当前入口只是导航骨架；这些功能并未接入 Hub。未接入提示也是固定文案，不表示应用已经执行连接检查。两个 Tab 的状态由 `TabShell` 保留，返回应用页时保留网格位置。

## 设计方向

优先服务于家庭平板“走近屏幕、扫一眼、点一下”的使用方式。借鉴车机界面稳定的入口位置、状态清晰、控件易点和较浅的层级；不照搬驾驶场景的尺寸或功能限制。大图标配文字，主操作保持充足间距，避免把状态只藏在颜色或动画里。

应用页像车机的应用启动器，收纳功能入口；总览页未来可以放家庭状态、常用控制和重要异常。因为总览内容尚未确定，当前只保留占位，不呈现虚构的温度、设备状态或可点的假控制。

## 页面展开方式

| 层级 | 现在 | 后续接入 Hub 后 |
| --- | --- | --- |
| 一级 Tab | 应用、总览 | 如有明确高频需求，再增补 Tab；不预先加空页 |
| 应用入口 | 每个图标进入标题对应的占位页 | 逐个替换为房间、设备、场景等真正的功能页 |
| 功能详情 | 返回应用页 | 设备详情、控制反馈、设置等按各功能需要展开 |

入口页只负责跳转。未来设备状态和控制命令经由共享 Repository 获取与发送；页面不直接调用 Hub。Hub 是设备状态的权威来源，操作后要显示发送中、已确认或失败；离线或过期数据必须清楚标注。门锁、警报等敏感控制需要明确的确认流程。

## 布局与交互

- 应用网格使用可纵向滚动的布局。图标数量和窗口尺寸变化时自动换列；底部为悬浮切换栏留出空间，最后一行不被遮住。
- 悬浮切换栏始终靠近屏幕底部，两个 Tab 直接切换，不用先返回首页。它是一级导航，功能详情页不显示它。
- 功能详情页保留明显的返回入口。后续接入实际功能时，返回应恢复原 Tab 和滚动位置。
- 优先按可用窗口宽度调整布局，不锁定横屏。横向平板是主要设计画布，窄屏仍需可读、可点。

[Flutter 自带的 `CupertinoSlidingSegmentedControl`](https://api.flutter.dev/flutter/cupertino/CupertinoSlidingSegmentedControl-class.html)提供滑动选中效果；官方 [go_router 多分支导航示例](https://github.com/flutter/packages/blob/main/packages/go_router/example/lib/stateful_shell_route.dart)展示了页面层级扩大后的做法。当前只有两个 Tab，先用 Flutter 自带的 `IndexedStack` 和标准页面导航即可。[Flutter 大屏建议](https://docs.flutter.dev/ui/adaptive-responsive/large-screens)强调按可用空间组织网格与导航；[车载视觉原则](https://developers.google.com/cars/design/design-foundations/visual-principles)强调一眼可读和一致的触控目标。

## 下一步

1. 确定「总览」要放的真实信息与高频操作，再做页面设计。
2. 确定优先实现的功能入口，并与 Hub 约定数据和控制协议；未支持的入口继续明确标为占位。
3. 为真实功能补连接、加载、离线和操作反馈，再根据导航复杂度决定是否引入路由库。
