# HomeLab Panel 页面与交互规划

## 当前已落地的框架

Panel 目前只有一个应用桌面，交互参考手机系统：图标页左右滑动，常用应用栏固定在底部。后续只有在第二个一级页面的用途明确时才设计 Tab 切换。

```text
HomeLab Panel
└── 应用桌面
    ├── 可左右滑动、拖拽排序的图标页：房间、设备、场景等终端功能
    ├── 底部常用应用栏：长按拖入、交换位置、拖回图标页
    └── 点击图标 → 设置页或对应功能的占位页 → 返回桌面
```

常用栏初始放入房间、设备、场景，另有两个空位；桌面图标与常用栏排列都保存在终端本机。当前入口只是导航骨架，这些功能并未接入 Hub。未接入提示也是固定文案，不表示应用已经执行连接检查。

## 设计方向

优先服务于家庭平板“走近屏幕、扫一眼、点一下”的使用方式。借鉴车机界面稳定的入口位置、状态清晰、控件易点和较浅的层级；不照搬驾驶场景的尺寸或功能限制。大图标配文字，主操作保持充足间距，避免把状态只藏在颜色或动画里。

应用页借用车机应用网格的交互形式，收纳控制终端内的功能入口。进入房间、设备、场景等功能后，终端将通过本地 Hub 获取状态并发送控制请求。将来接入 Hub 后，可根据真实数据增加家庭状态、常用控制和异常信息；目前不呈现虚构的温度、设备状态或可点的假控制。AI Agent 的入口方式还没有确定，也不预设它一定是独立 Tab。

## 页面展开方式

| 层级 | 现在 | 后续接入 Hub 后 |
| --- | --- | --- |
| 一级页面 | 只有应用桌面 | 根据真实高频任务决定是否增加 Tab |
| 常用栏 | 可拖入、交换、移出，位置保存在本机 | 连接 Hub 后仍作为用户自己的入口排序 |
| 应用入口 | 设置已可使用，其他图标进入标题对应的占位页 | 逐个替换为房间、设备、场景等真正的功能页 |
| 功能详情 | 返回应用页 | 设备详情、控制反馈、设置等按各功能需要展开 |

入口页只负责跳转。未来设备状态和控制命令经由共享 Repository 获取与发送；页面不直接调用 Hub。Hub 是设备状态的权威来源，操作后要显示发送中、已确认或失败；离线或过期数据必须清楚标注。门锁、警报等敏感控制需要明确的确认流程。

## 布局与交互

- 图标网格按可用宽度调整列数，按高度决定每页行数；左右滑动切页，圆点显示当前页。
- 常用应用栏始终靠近屏幕底部，在图标页之间保持不动。长按桌面图标拖到另一个格子可调整位置，在页边停留可跨页；图标也可拖入常用栏，从常用栏拖回图标区可移出。功能详情页不显示常用栏。
- 功能详情页保留明显的返回入口。返回后恢复原来的应用页位置。
- 优先按可用窗口宽度调整布局，不锁定横屏。横向平板是主要设计画布，窄屏仍需可读、可点。

[Android Auto 应用启动器](https://developers.google.com/cars/design/android-auto/product-experience/system-ui/app-launcher)展示了图标入口的组织方式；这里按用户希望的手机桌面习惯改成横向分页和固定常用栏。[Home Assistant Dashboard](https://www.home-assistant.io/dashboards)可作为将来展示真实家庭状态和控制的参考。[Flutter 大屏建议](https://docs.flutter.dev/ui/adaptive-responsive/large-screens)可作为网格适配的参考。

## 下一步

1. 确定优先实现的家庭控制入口，并与 Hub 约定数据和控制协议；未支持的入口继续明确标为占位。
2. 根据实际使用方式设计 AI Agent 的调用位置和对话流程；在明确之前不增加 AI Tab。
3. 为真实功能补连接、加载、离线和操作反馈，再根据任务数量决定是否增加一级页面。
